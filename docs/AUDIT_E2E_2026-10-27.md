# End-to-end audit — 2026-10-27

Scope: the whole application was run for real and used like a person would use it, then attacked. This is **not** a test-suite report: the unit and
integration suites were already green (621 tests) when the audit started, and they missed every serious defect below because they run in jsdom / MockMvc
and never cross a real browser, a real database restart, a real container stop or real concurrency.

## 1. What was actually run

| Component | How it ran | Notes |
|---|---|---|
| PostgreSQL 15 | **Docker** (`docker compose up`, container `finguard-postgres`, host port 5433) | Flyway applied V1–V7 to an empty volume. Stopped and restarted mid-test. |
| AI service | **Docker** (image built from `ai/Dockerfile`, container `finguard-ai`, port 8000) | `/health` OK. Stopped and restarted mid-test. |
| Backend | Spring Boot on the host (`./mvnw spring-boot:run`, dev profile) against the Docker database | There is no backend or frontend Dockerfile in this repository, so "the Docker stack" is PostgreSQL + the AI service; backend and frontend run on the host, as `start.ps1` does. |
| Frontend | Vite dev server (`npm run dev`) in the **built-in browser pane** | Real browser, real backend. Registration, statement upload, dashboard, transactions, budgeting & goals, loans, investments, forecasting, scenario builder, responsive layouts, sign-out flow. |
| Test drivers | Python scripts in the session scratchpad (outside the repository) calling the real HTTP API | ~700 requests, synthetic Indian bank data (HDFC/ICICI/SBI/Axis/Kotak layouts, Indian digit grouping, UPI/NEFT/ACH/POS narrations). |

Not covered (be honest): screen reader pass in this audit; no real bank exports directly from net banking portals (sample data synthetic, KI-019); no production profile HTTPS or multi-day soak test; backend restart *during* an import was not re-executed (covered by existing `ImportRecoveryListener` tests); concurrency was 6–40 parallel clients, not distributed load.

## 4. Findings — open (documented trade-offs)

| ID | Sev | Finding | Why it is open / documented decision |
|---|---|---|---|
| O-02 | P3 | **Access tokens stay valid up to 15 minutes after logout or session revocation** (stateless JWT). | Accepted architectural trade-off for stateless JWT authentication without shared Redis token-blacklist overhead. The 15-minute token lifetime bounds exposure, and refresh tokens are revoked immediately in the database upon logout. Distributed token revocation list deferred to clustered v1.0.0 deployment. |
| O-10 | P3 | **`HttpOnly` refresh token cookie, rate limiter, and brute-force lockout window are in-memory (single backend instance only)**; a correct password during a throttle window is refused (429). | Single-instance in-memory design is intentional for local/embedded deployment without external Redis dependencies. Distributed rate limiting and shared token caches are deferred to multi-replica production deployment (v1.0.0). |
