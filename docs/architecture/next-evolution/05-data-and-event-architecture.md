# 05 — Data and Event Architecture

Labels: **[V]** verified (2026-10-28) · **[H]** historical claim · **[E]** estimate · **[A]** hypothesis · **[R]** recommendation. Diagram source: [`diagrams/event-flow.mmd`](diagrams/event-flow.mmd).

## 1. Data ownership and boundaries

PostgreSQL is the **only system of record**. Everything else is derived, disposable and reconciled.

| Store | Contents | Writer | Readers | Rebuildable from PostgreSQL? |
|---|---|---|---|---|
| `public` schema | users, refresh_tokens, transactions, loans, investments, upload_jobs, budgets, financial_goals, goal_contributions, saved_scenarios (V1–V7) **[V]** | **Spring Boot only** (`finguard_app`) | Spring Boot; reconciler, Airflow via read-only role | — (this is the truth) |
| event publication registry / `processed_event` (S1) | domain event rows and consumer inbox | Spring Boot | Spring Boot; reconciler (lag check) | n/a (operational) |
| `analytics` schema (S2) | per user-month summaries (income, expenses, refunds, category net spend) | analytics-refresh consumer | API read paths (optional), reconciler, Airflow | **Yes — truncate and recompute** |
| Airflow metadata DB (S2) | DAG runs, task state | Airflow | Airflow | n/a — **separate instance/database; no ledger data** |
| Object storage (S3) | backups, Parquet exports, evaluation artifacts | CI, Airflow, backup job | operator | exports yes; backups are the recovery source |
| Valkey / ClickHouse / vector DB | **not introduced** | — | — | — |

**Data-flow boundaries:** financial data never flows *into* the AI service beyond the three fields it needs (`description`, `type`, `amount`), never into telemetry, and never into Airflow's metadata DB. Narrations (free text with merchant/person names) are the most sensitive field — keep out of events, logs, traces and exports unless an export is explicitly the user's own data export.

## 2. Schema evolution rules

1. **Flyway only; V1–V7 immutable.** Hibernate stays at `ddl-auto=validate` **[V]**.
2. **Expand → migrate → contract**, each in separate releases when the old code could still run (rolling deployments): add nullable column/table → deploy code writing both → backfill in batches → deploy code reading new → add `NOT NULL`/drop old only in a later release.
3. **Constraints are added `NOT VALID` then `VALIDATE CONSTRAINT`** to avoid long locks. Example (S1-07): `ALTER TABLE transactions ADD CONSTRAINT ck_transactions_amount_positive CHECK (amount > 0) NOT VALID; … VALIDATE CONSTRAINT …;` — the current schema has the check only in the service layer **[V — V1]**.
4. **New tables use `uuid` primary keys and `timestamptz`.** Existing `varchar(255)` ids and zone-less `timestamp` columns stay (changing them is a risky rewrite for no user-visible gain); the mixed convention is recorded in ADR-006 so it is deliberate, not accidental.
5. **Indexes are created `CONCURRENTLY`** in production-bound migrations (Flyway: `executeInTransaction=false` for those scripts).
6. **Every migration has a recovery plan** in its header comment (revert statement or "restore from PITR to <time>") and is rehearsed on staging with a copy of *synthetic* data at 10× expected size.
7. **Migrations run as a pre-deploy step** under a dedicated DDL role (`finguard_migrator`), not by every app replica at startup, once there is more than one replica.

## 3. Event catalog and schemas

**Why events at all?** Not to feed a broker, but to **decouple derived data and side effects from the ledger write**: refreshing analytics, writing audit records, purging derived data on deletion, measuring review decisions for model governance. All of these can be done in-process, transactionally safe, with no new infrastructure.

### 3.1 Envelope (CloudEvents-style, JSON)

```json
{
  "id": "0194c4e7-5a1b-7d2e-9f3a-6c1d2b8e4a90",
  "type": "com.finguard.import.completed",
  "schema_version": 1,
  "source": "finguard-backend/ingestion",
  "time": "2026-10-28T09:15:02.481Z",
  "subject": "upload_job/6f0b0e5e-0c7f-4d0e-9d57-0a1b2c3d4e5f",
  "tenant": "user:3f6c…",           
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "data": { }
}
```
`id` is a UUIDv7 generated by the publisher (time-ordered, collision-free); `tenant` is the internal user id (never email/name); `data` never contains narrations, names, e-mail addresses or free text.

### 3.2 Event types (v1)

| Event | Emitted when | `data` fields | Consumers |
|---|---|---|---|
| `import.completed` v1 | An import job reaches `COMPLETED` | `importJobId`, `bank`, `rowsProcessed`, `duplicateRows`, `rejectedRows`, `skippedRows`, `statementFrom`, `statementTo`, `classificationStatus`, `classifiedRows` | analytics-refresh; audit-writer; (metrics) |
| `ledger.period_changed` v1 | Any committed insert/update/delete that changes a month's figures (import, manual CRUD, category change, direction change) | `affectedMonths[]` (`YYYY-MM`), `cause` ∈ {`IMPORT`,`MANUAL`,`CATEGORY`,`DELETE`} | analytics-refresh (coalescing) |
| `transaction.category_reviewed` v1 | A person confirms, changes or clears a category | `transactionId`, `decision` ∈ {`CONFIRMED`,`CHANGED`,`CLEARED`}, `previousCategory`, `newCategory`, `previousSource` ∈ {`NONE`,`RULE`,`MODEL`,`USER`}, `ruleId?`, `modelVersion?` | model-governance metrics (review-rate, correction-rate per rule); audit-writer |
| `account.deletion_requested` v1 | A user asks to delete their account | `requestedAt`, `graceUntil` | privacy (purge derived data), audit-writer |

**Deliberate non-events:** one event per transaction (too chatty, no consumer), balance snapshots (no balance concept exists — KI-009/037), anything from the AI service (it is stateless and has no event output).

### 3.3 Rules for schema evolution

* One JSON Schema per `(type, version)` in `contracts/events/`.
* **Within a version: additive and optional only.** Never remove, rename or change the meaning of a field; never tighten a type.
* **Breaking change → new `type` or `schema_version` 2**; the publisher dual-publishes v1 and v2 for ≥ 2 minor releases; each consumer declares the versions it accepts; v1 is removed only after the oldest consumer is gone.
* CI: (a) every event class serialises to a document valid against its schema; (b) a fixtures directory holds *last release's* serialised events and the current deserialiser must accept them (backward compatibility); (c) a schema diff check blocks removals.
* A schema registry is **not introduced** while producers and consumers share a repository and a deployable; the repository *is* the registry. (A registry with compatibility modes becomes part of the broker gate, §7.)

## 4. Outbox, inbox, delivery and replay

### 4.1 Outbox (producer side)

**Choice:** Spring Modulith's JDBC *event publication registry* (S1-02) — events published with `ApplicationEventPublisher` inside the ledger's `@Transactional` method are persisted in an `event_publication` table **in the same transaction**; the registry resubmits incomplete publications at restart and on a schedule. **DDL is owned by Flyway** (Modulith's automatic schema init disabled). If a broker is ever introduced, a small relay reads the same table (or a dedicated `event_outbox` table, below) and publishes.

Dedicated outbox table (proposed only for the broker case):

```sql
-- Proposed V8+ (broker gate only). Recovery: DROP TABLE event_outbox (no other table depends on it).
CREATE TABLE event_outbox (
    id             uuid PRIMARY KEY,
    aggregate_type text        NOT NULL,
    aggregate_id   text        NOT NULL,
    event_type     text        NOT NULL,
    schema_version integer     NOT NULL,
    occurred_at    timestamptz NOT NULL DEFAULT now(),
    payload        jsonb       NOT NULL,
    published_at   timestamptz,
    attempts       integer     NOT NULL DEFAULT 0,
    last_error     text
);
CREATE INDEX ix_event_outbox_unpublished ON event_outbox (occurred_at) WHERE published_at IS NULL;
```
Ordering guarantee: **per aggregate (per user)**, by `occurred_at, id`; no global ordering is promised or needed because consumers recompute from the ledger.

### 4.2 Inbox (consumer side)

```sql
-- S1-02/S2-05. Recovery: DROP TABLE processed_event.
CREATE TABLE processed_event (
    consumer     text        NOT NULL,
    event_id     uuid        NOT NULL,
    processed_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer, event_id)
);
```
Consumer algorithm: begin tx → `INSERT … ON CONFLICT DO NOTHING` into `processed_event`; if 0 rows inserted → duplicate, commit and return; else perform the effect (recompute from ledger), commit. Inbox row and effect commit atomically, so crash-and-retry yields exactly one *effect* even though delivery is at-least-once.

### 4.3 Delivery guarantees

| Property | Guarantee |
|---|---|
| Producer atomicity | event persisted iff ledger change committed (rollback test) |
| Delivery | **at-least-once**; duplicates possible after crash/retry |
| Effect | **effectively-once** via inbox + recompute-from-ledger design |
| Order | per aggregate by `(occurred_at, id)`; consumers must not depend on cross-user order |
| Latency target | p99 publication → consumer complete ≤ 60 s (SLO-5, proposal) |
| Retention | completed publications purged after 14 days **[E]**; failed kept until resolved |

### 4.4 Retries, dead letters, replay, recovery

* **Retry:** exponential backoff 1 s → 5 min, max 8 attempts, jitter; only for idempotent consumers (all are).
* **Dead letter:** after the last attempt the publication is marked failed and copied to `event_dead_letter` (id, listener, payload, error, attempts); alert fires when count > 0 for 15 min.
* **Replay:** an operator command (`POST /internal/events/replay?type=…&from=…&to=…` or a runbook SQL + trigger) republishes by id or time range. Safe because consumers are idempotent *and* recompute rather than apply deltas.
* **Full rebuild:** truncate `analytics`, enqueue `ledger.period_changed` for all user-months (batched, rate-limited). Doubles as the DR test for derived data.
* **Poison events:** a malformed payload goes to dead letter on the first deserialisation failure (no retry); alert + fix + replay.
* **Consumer crash mid-effect:** transaction rolls back (inbox row too); redelivery repeats the effect.
* **Backpressure:** publication registry processed by a bounded executor; if lag exceeds threshold, the lag metric alerts; the ledger write path is never blocked by consumers (events are persisted, not delivered, inside the write transaction).

### 4.5 Failure-mode table

| Failure | Effect | Detection | Recovery |
|---|---|---|---|
| Backend crashes after commit, before delivery | Event persisted, not delivered | publication-lag metric, restart resubmission | automatic on restart |
| Consumer bug throws | Retries, then dead letter | dead-letter alert | fix, replay |
| Duplicate delivery | Skipped by inbox | inbox conflict counter | none needed |
| `analytics` corrupted or stale | Reads wrong summaries | **reconciler delta ≠ 0** | truncate + rebuild from ledger |
| Event schema mistake in release N | Consumer can't parse | contract test in CI; dead letter in prod | roll back release (rows remain valid under v1) or hot-fix consumer; replay |
| Publication table grows unbounded | Disk/latency | table size alert | purge job; investigate stuck listeners |
| Database outage | API 503 (**[V]** fast fail), no events lost (nothing was committed) | health probe, SLO burn | managed failover/PITR |

## 5. Analytics architecture — when PostgreSQL is enough

**Position:** PostgreSQL is sufficient now and for a long time. The audit reports every analytics/forecast endpoint under 340 ms on a 10,000-row ledger **[H, not re-run]**; a per-request 36-month bounded read is the design **[V — ARCHITECTURE §9]**.

Staged escalation, each step triggered by a **measured** condition and each preserving exact decimal semantics (`numeric`, scale 2, HALF_UP in Java; the SQL path must produce identical rounding — verified by the golden dataset):

| Level | Trigger (measured on staging with synthetic scale data) | Action |
|---|---|---|
| L0 (today) | p95 analytics < 500 ms at 10k tx/user | per-request reads |
| L1 | p95 > 500 ms at target user size, or dashboard fan-out > 6 queries | `analytics.monthly_summary` table maintained by the analytics-refresh consumer (derived, rebuildable) |
| L2 | table > ~100 M rows or index maintenance dominates | declarative partitioning of `transactions` by `txn_date` (range, yearly), partial indexes |
| L3 | Cross-user analytical questions (cohorts, product metrics) that must not touch OLTP | nightly export to Parquet (object storage) + DuckDB/Polars **offline**; read replica |
| L4 | Interactive analytical queries over > 200 M rows with p95 > 2 s on L1–L3 | evaluate ClickHouse (LTS) **as a read-only derived store** fed from Parquet/outbox; never a second system of record |

**Reconciliation (mandatory at every level):** the Go reconciler recomputes from `public.transactions` and requires **exactly zero** difference to the derived store; mismatches page. Aggregates are decimal strings end-to-end (no float in exports; Parquet uses `DECIMAL(38,2)`).

## 6. Data contracts, quality and lineage

| Dataset | Contract | Quality checks (run by Airflow/CI) | Lineage |
|---|---|---|---|
| `transactions` | schema + constraints (V1, V3, V5) | row counts vs `upload_jobs` reconciliation identity; no direction/category mismatch; dates within [1990-01-01, tomorrow]; scale ≤ 2 | import job → rows (`import_job_id`) **[V]** |
| `analytics.monthly_summary` | `contracts/analytics/monthly_summary.json` | zero delta vs recomputation | derived from ledger by event id |
| Evaluation datasets | manifest: file name, SHA-256, row count, label provenance (`synthetic`/`real-consented`), author, created, frozen-holdout flag | hash matches; no overlap between dev and holdout; label distribution report; `synthetic` flag propagates to every report title | manifest in Git; artifacts in object storage |
| Parquet exports | JSON schema, `DECIMAL(38,2)` | row counts equal source; sum equality per month | export run id → DAG run |

Lineage tooling (OpenLineage/Marquez) is **deferred**: with ~5 datasets the manifest + DAG graph is sufficient.

**Reproducible datasets:** synthetic generators take an explicit seed and a version; the generator + seed + code SHA reproduce byte-identical output (checked in CI). **No production data is used in synthetic evaluation or development (principle 13).**

## 7. The streaming-platform gate (decision: *not now; maybe later; possibly never*)

Introduce Kafka (4.x, KRaft) — or Redpanda as a Kafka-API implementation — **only if at least two** of the following are *true and measured*:

1. ≥ 2 independently deployed consumers (separate release cadence) need the same events;
2. sustained event rate > 500/s or bursts the PostgreSQL publication table cannot absorb with the ledger write path healthy;
3. a consumer needs multi-day replay without touching PostgreSQL (e.g., a new ML feature backfill);
4. an external team/partner must subscribe;
5. stream processing (windowed joins/aggregations) that SQL cannot express.

**Today:** condition 1 false (all consumers are in-process), 2 false (**[E]** < 1 event/s even at 10k active users: ~15 events/user/month ⇒ ≈ 150,000/month ≈ 0.06/s), 3–5 false. RabbitMQ is rejected (a Postgres job table covers task queues); Pulsar rejected.

**If the gate fires:** pilot (S2-08) = outbox relay (Go or Debezium) → Kafka topic per event type (`finguard.import.completed.v1`), key = `tenant`, partitions = 6 **[E]**, retention 7 days, compacted DLT, JSON Schema in a registry with `BACKWARD` compatibility, consumers keep the inbox. Operational cost (cluster, upgrades, ACLs) is recorded in [10](10-cost-and-operational-model.md); rollback = stop the relay (outbox remains the source of truth).

## 8. Retention, deletion and privacy in the data layer

| Data | Retention | Deletion mechanics |
|---|---|---|
| Ledger rows, budgets, goals, scenarios | until account deletion | account deletion: soft-delete flag + 30-day grace **[E, decide with counsel]**, then hard delete in one transaction per table with `ON DELETE CASCADE` verified by test (budgets, goals, contributions, scenarios, refresh tokens already cascade **[V — V2, V6, V7]**; `transactions`, `loans`, `investments`, `upload_jobs` FKs have **no** cascade **[V — V1]** → explicit ordered delete, see below) |
| `upload_jobs.row_errors_json` (sanitised snippets) | 90 days **[E]** | scheduled purge |
| `refresh_tokens` | until expiry + 7 days | scheduled purge exists **[H]** |
| Event publication, inbox | 14 days / 30 days **[E]** | purge job |
| `audit_log` | 1 year **[E]**, append-only | partition drop; user id hashed after deletion |
| Backups | 35 days **[E]** | lifecycle rule; deletion propagates within the backup window (documented in the privacy notice) |
| Derived `analytics`, exports | until next rebuild / deletion | purge on `account.deletion_requested` |
| Telemetry | 14 days traces, 30 days metrics, 14 days logs **[E]** | backend retention; no PII to begin with |

The ordered-delete requirement is a concrete finding **[V — V1, V3]**: all four tables created in V1 (`transactions`, `investments`, `loans`, `upload_jobs`) reference `users` **without** `ON DELETE CASCADE`, and `transactions.import_job_id` references `upload_jobs` (also without cascade), so a naïve `DELETE FROM users` fails with an FK error. S1-05 must include the explicit deletion order (transactions → upload_jobs → loans/investments → remaining user-owned rows → user) and a test that creates data in every table and verifies zero residual rows.
